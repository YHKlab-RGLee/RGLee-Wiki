# 문서별 독립 agent 운영 규약

메인은 문서별 작업 배정, 결과 통합, 공용 품질 상태 갱신과 최종 검증을 담당한다. 기존 과학적 기준, 스킬의 필수 단계, CLI, 평가 schema와 publication gate는 그대로 유지한다.

## 역할과 작업 단위

| 역할 | 스킬 | 책임 |
| --- | --- | --- |
| `wiki_revision` | `revise-wiki-article`; 신규·대규모 개정은 `research-and-write-wiki` | 근거 있는 작성·수정 |
| `wiki_references` | `audit-wiki-references` | 최종 문서의 주장과 원문을 독립 대조 |
| `wiki_quality` | `assess-wiki-article` | 최종 문서를 기존 rubric으로 독립 평가 |
| 메인 | 기존 `evaluate-wiki-quality` 진입점 | 절차 연결·등록·최종 검증 |

각 subagent는 한 문서의 한 역할만 담당한다. 다른 문서를 맡기거나 작성자를 검토자로 전환하지 않는다. 선행 문서를 읽는 것은 허용하지만 그 문서의 수정·평가까지 담당 범위에 추가하지 않는다. 여러 문서에 걸친 수정은 메인이 문서별 작업과 선후 의존 관계로 나눈다.

## 작업 배정과 독립 입력

메인은 전체 요청을 문서별로 나누어 기본적으로 순차 처리한다. 실제 실행 한도 안에서 필요한 역할을 배정하며, 동시 실행 한도를 전체 요청 문서 수의 제한으로 사용하지 않는다. 일시적인 생성 제한은 실행 중인 작업의 완료를 기다린 뒤 재시도한다. 계속 진행할 수 없으면 완료한 작업과 남은 작업을 보고하며, 자체 평가로 독립 검토를 대체하지 않는다.

Navigation/presentation 등 독립 과학 검토가 필요 없는 작업은 기존 경로를 유지한다. 검사만 요청받고 수정 역할을 추가하지 않는다.

1. 문서·역할별로 새 subagent를 배정한다. `spawn_agent`에 `fork_turns`가 있으면 `none`을 사용한다. 다른 문서의 작업 대화는 전달하지 않는다.
2. 작성자에게는 해당 문서의 수정 목적·범위·기존 변경과 필요한 근거를 전달한다. 검토자는 최종 문서, 검토 기준, 필요한 선행 문서와 중립적인 사용자 제약만 받는다. 작성 대화·자기평가·이전 점수·통과 기대·작성자의 근거 요약·다른 검토자의 결론은 초기 입력에서 제외한다.
3. 검토자는 과거 점수를 찾아 읽지 않고 자신의 초기 발견 사항을 먼저 기록한다. 이후 참고문헌 결과나 기존 유효 근거를 범위·provenance에 맞게 대조한다. 다른 agent의 보고를 자신의 직접 원문 확인으로 기록하지 않는다.
4. 같은 문서의 수정·재검토는 각 담당자가 이어간다. 담당자를 교체할 때도 같은 독립 입력 원칙을 적용한다.

## 문서 처리 순서와 파일 책임

수정 → 최종 버전 고정 → 독립 참고문헌·품질 검토 → 결과 대조 → 필요한 수정·재검토 → 등록·최종 검증의 순서이다. 작성자는 기존 직접 출처 확인 의무를 유지한다. 두 검토자는 같은 고정 버전을 읽고, 실행 한도가 허용하면 병렬로 검토한다. 품질 담당은 초기 판단을 남긴 후 참고문헌 결과를 반영한다. 메인은 점수를 평균하거나 실패를 임의로 pass로 바꾸지 않는다.

기본적으로 한 문서의 등록·최종 검증을 마친 뒤 다음 문서로 진행한다. 문서별 수정 담당은 한 명이며 검토 중에는 그 버전을 수정하지 않는다. 선행 문서나 공유 그림·정의가 바뀌면 영향을 받는 검토도 다시 확인한다. 검토자는 본문·registry·정책을 수정하지 않고 고유한 `experiment/<request>/<document>/<role>/`에만 결과를 작성한다.

전체 문서 검토 요청은 본문 전체를 읽는다. 국소 수정의 출처 대조는 변경 주장과 영향을 받는 결론을 대상으로 하고 신규 문서는 새 주장 전체를 다룬다. 전체 citation audit을 요청하지 않았으면 기존 인용 전체로 자동 확대하지 않는다. Full review는 여전히 모든 criterion을 평가하며 실제 확인·재사용·미확인 범위를 구별한다.

메인은 `quality.sh sync`, `quality.sh review`, 최종 build를 직렬 실행한다. 읽기 전용 검사·개별 검산은 담당자가 수행할 수 있다. 본문 hash가 바뀌면 오래된 평가를 등록하지 않는다. 실행하지 않은 검증은 pass로 기록하지 않는다. Pending 상태에서 strict-render 증거를 확보하는 절차와 최종 publication gate의 구분은 `evaluate-wiki-quality`를 따른다. 검토 모델은 실제 평가자의 확인된 값만 기록하며 불명확하면 공백으로 둔다.

## 간결한 입출력

공통 규칙과 스킬 전문은 메시지마다 복사하지 않고 경로로 참조한다. 역할 TOML과 저장소 루트는 작업 지시에 포함한다. 아래 예시의 경로·값은 실제 작업에 맞춰 채우며, 작업 범위와 권한에 필요한 추가 지시만 붙인다.

```yaml
task_id: <문서-역할 식별자>
role: <wiki_revision | wiki_references | wiki_quality>
document: <대상 Markdown 경로>
version: <입력 파일 SHA-256; 신규 문서는 null>
scope: <수정 범위 또는 full/outline/감사 범위>
constraints: <이번 요청의 추가 제약>
output_dir: <고유한 experiment 경로>
```

응답은 아래의 짧은 상태 정보로 제한하고 상세 근거·지적사항·평가 YAML은 파일로 남긴다. 중간 로그를 매 단계 메인에 보내지 않고 막힘·버전 충돌·중요한 범위 변경·완료 시 알린다.

```yaml
task_id: <같은 식별자>
version: <작성자가 산출하거나 검토자가 실제 읽은 파일 SHA-256>
status: <completed | changes_required | blocked | stale>
verdict: <pass | revise | unverified | not_applicable>
summary: <핵심 결과 한두 문장>
blocking_findings: <해결되지 않은 핵심 문제 수>
result_path: <상세 결과 파일>
```

`completed`는 맡은 작업의 완료이며 문서 품질 통과와 별개이다. 감사가 완료되어 오류를 찾았다면 `completed`와 `revise`가 함께 올 수 있다. 작성 결과의 verdict는 `not_applicable`이며 작성자가 최종 pass를 부여하지 않는다. 자료 접근 실패는 `blocked`/`unverified`, 작업 도중 대상 버전 변경은 `stale`/`unverified`로 보고한다. 수정 지적을 발견한 것과 평가 자체를 완료하지 못한 것을 구별한다.

메인은 결과 파일의 존재, task_id, 문서 버전, 필수 필드와 실제 판정을 대조한다. 실패·불일치·수정 판단에 필요한 상세 근거를 읽고, 등록 시 기존 assessment와 검증 결과를 확인한다. 형식이 잘못됐거나 결과 파일이 없으면 완료로 처리하지 않는다. 이 전달 형식은 작업 통신용이며 기존 quality registry·assessment schema를 바꾸지 않는다.

## 최소 진행표와 실행 환경

메인은 `experiment/<request>/tasks.yaml` 하나에 문서·버전·역할·작업 상태·결과 경로를 기록한다. 재개 시 실제 파일과 작업 결과를 재확인한다. 이미 완료된 검증을 이유 없이 반복하거나 이전 채팅 기억만으로 완료를 판정하지 않는다.

모델·reasoning effort·sandbox·도구는 역할 설정에서 새로 강제하지 않고 유효 실행 설정을 따른다. 검토자의 본문 수정 금지는 현재 역할 지침이며 별도 파일시스템 격리와 동일하지 않다. Custom agent 선택을 지원하면 역할 TOML을 사용하고, 그렇지 않으면 담당 subagent에 해당 TOML의 `developer_instructions`를 읽도록 전달한다.
